# Wear companion

The Wear app uses the phone's current school timetable, an explicitly requested AI relay, and an optional independent school connection. The default timetable/AI companion does not store school credentials. Gradey ID and Firebase tokens stay on the phone in every mode. The phone and watch use the same application ID; production artifacts must also use the same signing certificate for Google Play Services Data Layer communication.

## Timetable, Tile and complication

The watch stores a versioned, credential-free snapshot. A newer signed-out snapshot removes the previous user, timetable and AI identity. Timetable selection excludes canceled lessons, accounts for current and future lessons, and refuses a snapshot older than seven days. The main screen shows progress, remaining minutes, grouped upcoming lessons, changes and the cache timestamp. Refresh sends a request to the phone and only reports success after receiving a newer snapshot. Connection and response waits are bounded.

`GradeyLessonTileService` supplies a 24-hour system timeline, with entries at lesson starts, lesson ends and cache expiry. Its untimed fallback asks for a refresh. `GradeyLessonComplicationService` provides `SHORT_TEXT`, `LONG_TEXT` and `RANGED_VALUE` timelines, including system countdown text and dynamic current-lesson progress where supported. Empty, signed-out and stale states provide no complication data. A user-selected Tile or complication displays timetable information; it does not contain marks, AI text, account tokens or login details. Adding a watch-face complication is an explicit user action. Hosts that do not support timeline entries may display the safe no-data fallback.

## Explicit AI relay

The watch's **Ask a question → Review → Send question** flow uses the Wear system input screen. Sending is a user action; neither opening the screen nor synchronizing the timetable generates a reply. Questions use general reply mode and do not automatically attach school records. The phone checks the existing AI consent, current signed-in owner and school scope, configuration, active recurring supporter eligibility, and available Compute. This does not grant consent or start a subscription.

The shared protocol binds requests and responses to an opaque owner/school identity, UUID request/client-message IDs, and the phone node that supplied the snapshot. Requests expire after two minutes. Input is limited to 2,000 Unicode code points; packets are limited to 48 KiB; answers are limited to 40,000 code points. Response sequences buffer at most 32 missing positions and ignore duplicates. A terminal response with no replacement text retains the accumulated answer. A changed identity cancels the active request and clears the watch's draft, answer and conversation.

The watch waits at most ten seconds for each connection/send operation and two minutes for a reply. It sends cancellation on Stop, timeout, invalid stream or destruction of the screen model. Late responses cannot mutate a different request. The phone independently caps execution at 110 seconds and validates the identity again around asynchronous work. The phone's durable request journal stores recovery identifiers and a request fingerprint, not prompts. It prevents reissuing a paid generation when the same client-message ID is explicitly retried. The watch offers an explicit **Retry same request** action after uncertain connection, timeout or request failures, preserving the original client-message ID, question, locale and chat reference while refreshing only transport correlation and expiry. New chat, a new send and identity changes clear recovery. It does not automatically retry or keep questions/answers on disk; interrupted replies can also be checked on the phone.

## Optional independent school connection

Independent refresh is off by default. The phone must explicitly grant a particular nearby watch access to its current school account; the watch then explicitly connects from **School on watch**. Each grant has a maximum seven-day expiry. Provisioning requires the same nearby node, current owner and school scope, canonical student identity, and unchanged grant before and after asynchronous work. A watch screen lock is required. Grant renewal is an explicit phone action, never an automatic extension.

The watch creates a non-exportable Android Keystore RSA key for a single, two-minute challenge. The phone seals only the school username/password and verified provider identity using an AES-GCM envelope bound to the request, scope, grant and lease, with an RSA-OAEP wrapped key. Provider tokens, phone cookies, Gradey ID and Firebase credentials are never copied. Credentials and the resulting watch-only session are encrypted with a separate Android Keystore AES key; backup is disabled and supported platforms require the device to be unlocked before key use. Secrets do not enter the public timetable DataItem. Pending keys are deleted after use or expiry.

The watch logs in directly to Bakaláři or EduPage and obtains its own token/cookie family. It renews only its own Bakaláři refresh token, handles EduPage code/approval verification, selects only the granted student, and checks the canonical provider user ID before requesting a timetable. Captcha and missing/revoked credentials have explicit reconnect paths. Refresh uses a bounded request and a single connection owner to avoid concurrent refresh-token redemption. The timetable refreshes on explicit request and on opening the app when its cache is older than five minutes; there is no perpetual background poll.

Received sign-out, account switches, replaced grants and revocations synchronously erase the private connection. Expired grants and removal of the watch screen lock also fail closed. An in-flight refresh cannot restore a removed connection or write another school's timetable. An offline watch cannot receive an immediate remote revocation; its existing connection stops at the displayed lease expiry at the latest, and a received revocation stops it sooner. **Remove from watch** deletes the local connection without silently provisioning another one.

## Verification and remaining acceptance

Focused checks passed on 29 September 2026: `:core-domain:test`, `:core-network:test`, `:wear:assembleDebug`, `:wear:assembleDebugAndroidTest` and `:wear:lintDebug` (`/tmp/gradey-watch-independent-tests.log`). No lint errors were suppressed. Shared tests cover lesson boundaries, stale and signed-out data, protocol validation, reordered and duplicate responses, source/owner/request rejection and answer bounds. Independent connection fixtures cover encrypted envelope correlation/tampering/expiry, separate refresh families, identity rejection and EduPage approval/student selection. The phone AI relay has twelve mocked tests; no live paid generation or actual credentials were used.

On the dedicated small round Wear OS 6 emulator, all **11 instrumentation tests pass without skips** (`/tmp/gradey-wear-secure-device-final.log`). Six exercise actual Android Keystore operations with synthetic credentials and a configured emulator screen lock, including sealed provisioning, rejection, revocation and reconnection isolation. Five cover UI and unavailable-phone recovery. These checks do not establish physical pairing or live provider acceptance.

Before release, verify phone/watch pairing and identical signing, both locales on round and rectangular watches, Tile and watch-face host rendering, transition/ambient behavior, phone disconnection, streamed answers, cancellation, quota/consent errors, account switching and sign-out. Physical-device battery behavior and live Firebase/App Check/subscription integration remain acceptance gates. The checked-in Wear version/signing defaults require a coordinated Play Wear artifact release configuration.

Implementation follows the official [Tile documentation](https://developer.android.com/training/wearables/tiles/get_started), [complication data-source guidance](https://developer.android.com/training/wearables/complications/exposing-data), [Wear input helper](https://developer.android.com/reference/kotlin/androidx/wear/input/RemoteInputIntentHelper), [Wear task/Recents guidance](https://developer.android.com/training/wearables/apps/launcher), [Data Layer security guidance](https://developer.android.com/training/wearables/data/overview), and [Android Keystore documentation](https://developer.android.com/privacy-and-security/keystore).
